### 1.1 最该知道的三件事

**① 整书资产卡曾经从来没生成过。**
`_assemble_after_analysis` 的 manifest 只有 `{"title": ...}`，缺 `selected_indices` → voice-card 的 `sample_chapters` 恒为 `[]` → `validate_voice_card` 要求 ≥3 项 → 校验必失败 → `_write` 静默跳过落盘。
后果：结果页资产全空、报告 0 字、铁律二必判失败，日志里只有一行 warning。
**教训**：`_write` 的"校验失败就跳过"是正确策略，但没有任何出口告诉上层"从来没成功过"。

**② `normalize_pass3` 会编造数据。**
按 `prompts/pass3_style.md` 的规范输出 `chapter_opening_patterns: [{pattern: 直入对话, frequency: 4}]`，落盘变成 `[场景白描×3, 内心独白×2]` —— 因为原实现只认 `isinstance(str)`，list 被丢弃后落进"从 pov 推导默认模式"的兜底分支。
磁盘上 7 张 voice-card 有 5 张开篇模式完全相同，全是这一条编造的。
**教训**：编造具体数字比缺字段更有害——用户会以为那是书的真实规律。

**③ 前端 `deepToCamel` 把 11 处 snake_case 读取点打成 `undefined`。**
最严重的：资产编辑器把 `content`（资产 JSON 本体）原样存进文本框、原样回传，落盘即 camelCase。实测一张 **0 校验错误**的 voice-card 走一遍「详情→保存」后 `validate.py` 报 **9 个硬错误**，界面仍提示「保存成功」。
**教训**：`client.ts` 的 `deepToCamel` 转**所有层级**的键。凡是「会被原样写回后端」的载荷必须走 `getRaw()`（本次新增）。

## 3. 踩过的坑（省你时间）

### 3.1 段错误的真正根因

`gui/db.py::get_conn()` 原实现在库路径变化时调 `_close_all_locked()`——**关闭所有线程的连接**，包括别的线程正在执行语句的那条。SQLite C 库里这是未定义行为，直接崩进程。

最小复现（本机 Windows，稳定 exit 139）：
```python
# 线程 A: 循环 with db.tx(): conn.execute("SELECT 1")
# 主线程: 反复切换 config.STATE_ROOT / DB_PATH 并调 get_conn()
→ Segmentation fault (core dumped)
```

修法：连接按 tid 记录自己绑定的路径（`_conn_bound_path`），路径变化只丢弃**本线程**那条。

**我在这上面错了三次**（改 `isolate_paths` 的清理策略），前两次都只是挪动表层症状。记录下来避免重走。

### 3.2 Bash heredoc 会吃转义

`python - <<'PYEOF' ... PYEOF` 里写 `"\\n"`、`"\\ud800"`、`"\\s"` 会被 shell 处理成真实字符，导致 SyntaxError 或写出含空字节的文件（实测把 `test_deslop_and_export.py` 整文件写坏过一次）。

**做法**：写文件内容一律用 Write 工具；必须用脚本时，用 `chr(92)` / `chr(0xD800)` 构造。

### 3.3 `git checkout -- <file>` 是恢复误操作的正确姿势

我误用 `s[:idx] + s[end:]`（`idx` 为 -1 时把文件清空）后，`git checkout -- tests/test_deslop_and_export.py` 立刻恢复。**但要先确认该文件的最新内容已提交**，否则会丢未提交的改动。
