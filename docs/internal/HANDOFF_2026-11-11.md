### 2.1 整书资产卡曾经从来没生成过（P0，已修）

**现象**：GUI 点「一键分析」，进度条走完显示「分析完成」，但结果页资产全空、
报告 0 字、铁律二必判失败。日志里只有一行 warning。

**根因链**：
```
_assemble_after_analysis 的 manifest 只有 {"title": ...}
  → 缺 selected_indices
  → assemble_voice_card 产出 sample_chapters: []
  → validate_voice_card 要求 ≥3 项，必然 ERR
  → _write 静默跳过落盘
```

**为什么没人发现**：`_write` 的「校验失败就跳过」策略本身是对的
（避免次品覆盖好卡），但**没有任何出口告诉上层「从来没成功过」**。

**修法**：`gui/services.py::_assemble_after_analysis` 补 `selected_indices` /
`selected_count`；GUI 是全章分析，索引取 `1..N`。

**提交**：`e5fe099`

### 2.2 normalize_pass3 会编造数据（P0，已修）

**现象**：按 `prompts/pass3_style.md` 的规范输出
`chapter_opening_patterns: [{pattern: 直入对话, frequency: 4}]`，
落盘变成 `[场景白描×3, 内心独白×2]`。

**根因**：原实现用 `fuzzy_find` 取到规范结构（list of dict）后要求
`isinstance(str)`，list 被丢弃 → 落进「从 pov 推导默认模式」的兜底分支 → 凭空造数。

**证据**：磁盘上 7 张 voice-card 有 **5 张**开篇模式完全相同，全是这一条编造的。

**为什么这条比缺字段更严重**：用户会以为那是这本书的真实规律。
**编造具体数字比留空更有害。**

**同批修的另外 3 个字段**：
- `emotion_handling.body_reaction_vocabulary` → 恒为 `[]`（只查顶层键，不查嵌套路径）
- `dialogue.subtext_level` → 硬编码 `"直白"`，从不读输入
- `narration.paragraph` → 硬编码 `{}`

**修法**：优先按 schema 精确路径读，取不到再退化到模糊匹配；兜底不再造数据。
`prompts/pass3_style.md` 本身也缺 `dialogue` 段（schema 要求 `subtext_level`
三档枚举，prompt 却没让模型输出）——两处一起补齐。

**提交**：`45f6c92`

### 2.3 前端 deepToCamel 把 11 处读取点打成 undefined（P0，已修）

**根因**：`gui/web/src/api/client.ts` 的 `deepToCamel` 转换**所有层级**的键。
凡按 snake_case 读取的地方全部拿到 `undefined`。

**最严重的后果——资产编辑器会把合法资产改废**：
```
assetApi.detail 走 get<> → content 被转成 camelCase
  → 编辑器原样 stringify 进文本框
  → 保存时原样回传
  → 落盘的即是 camelCase
```
实测：一张 **0 校验错误**的 voice-card，走一遍「详情→保存」后
`validate.py` 报 **9 个硬错误**，而界面仍提示「保存成功」。

**修法**：新增 `getRaw()`（`typedRequest` 加 `skipCamel` 参数），资产详情专用。
**这是唯一一处「会被原样写回后端」的载荷，必须保持 schema 原样。**

**其余 10 处**：宪法审查（2 个工作台直接崩）、手动入库回执、桥段徽标、
QC 截断提示、LitRPG 面板、平台标签等。

**一个值得记的细节**：5 个测试文件用 **snake_case mock**——组件测试喂 snake 数据、
组件读 snake、两边一起错，缺陷被完整掩盖。改成 camel 后测试才真正有意义。

**提交**：`ce1ae3d`

### 2.4 进程级段错误（P0，已修，我在这上面判断错了三次）

**现象**：CI 的 Ubuntu 三条腿反复 `Segmentation fault (core dumped)`（exit 139）。

**真正根因**：`gui/db.py::get_conn()` 在库路径变化时调 `_close_all_locked()`——
**关闭所有线程的连接**，包括别的线程正在执行语句的那条。
SQLite C 库里这是未定义行为，直接崩进程。

**最小复现**（本机 Windows 稳定 exit 139）：
```python
# 线程 A: 循环 with db.tx(): conn.execute("SELECT 1")
# 主线程: 反复切换 config.STATE_ROOT / DB_PATH 并调 get_conn()
→ Segmentation fault (core dumped)
```

**修法**：连接按 tid 记录自己绑定的路径（`_conn_bound_path`），
路径变化只丢弃**本线程**那条。

**我的三次误判**（写下来免得重走）：
1. 第一次：以为 `isolate_paths` 的 `_reset_conn()` 必须保留 → 改成「只关本目录的连接」，仍崩
2. 第二次：完全不做跨线程 close → 3.13 也崩了
3. 第三次：`_close_conns_under` 仍会跨线程 close → 3.12/3.13 崩
4. 真正根因在 `get_conn` 自身，不在测试隔离层

**提交**：`87fd237`（根因）、`40b15f0` / `7b93506` / `e804b39` / `fa6d3df`（过程中的尝试，多数已被后续覆盖）

### 2.5 load_state 无锁读覆盖并发写（P0，已修）

**现象**：Windows 上写 200 次，只剩 130 次。

**根因**：写者用「写唯一 tmp + `os.replace`」落盘。Windows 上 `os.replace`
与另一线程正打开的句柄互斥。读线程恰在替换瞬间 `open()` 会拿到
`Permission denied (WinError 5)`，而 `load_state` 把 `OSError` 一律当成
「文件损坏」，**返回一份空白状态**——随后 `update_state` 拿空白状态整份写回。

**实测对比**：
```
1 写者 200 次 + 1 读者持续读
  修前：n=130，日志 7 次「状态文件损坏」
  修后：n=200，零告警

50 章 × 4 批（200 批）+ 读者轮询 + 暂停/继续
  修前：136/200
  修后：200/200
```

**修法**：`load_state` 与写者共用同一把按路径锁。

**提交**：`aee06db`
